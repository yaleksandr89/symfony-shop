# OAuth

OAuth в Symfony Shop решает три разные задачи: обычный вход или регистрация гостя, явная привязка внешней учётной записи к уже существующему локальному пользователю и защищённая отвязка. Эти операции намеренно не объединены в автоматическое связывание по email.

## Поддерживаемые провайдеры

| Провайдер | Внутреннее имя | Семья локальной идентичности |
| --- | --- | --- |
| Google | `google` | `google_id` |
| Yandex | `yandex` | `yandex_id` |
| VKontakte | `vkontakte` | `vkontakte_id` |
| GitHub EN | `github_en` | `github_id` |
| GitHub RU | `github_rus` | `github_id` |
| Facebook | `facebook` | `facebook_id` |
| LinkedIn | `linkedin` | `linkedin_id` |

GitHub EN и GitHub RU — отдельные OAuth-клиенты с разными учётными данными и маршрутами, но они представляют одну семью идентичности и записывают один `github_id`.

Mail.ru присутствует только как намеренно неподдерживаемое значение. Для него нет клиента или входа; `OAUTH_MAILRU_ENABLED` должен оставаться равным `0`.

## Включение провайдера

По умолчанию все OAuth-возможности выключены. Для каждого реализованного провайдера нужны выключатель и пара учётных данных:

| Провайдер | Выключатель | Client ID | Client secret |
| --- | --- | --- | --- |
| Google | `OAUTH_GOOGLE_ENABLED` | `OAUTH_GOOGLE_ID` | `OAUTH_GOOGLE_SECRET` |
| Yandex | `OAUTH_YANDEX_ENABLED` | `OAUTH_YANDEX_CLIENT_ID` | `OAUTH_YANDEX_CLIENT_SECRET` |
| VKontakte | `OAUTH_VK_ENABLED` | `OAUTH_VK_CLIENT_ID` | `OAUTH_VK_CLIENT_SECRET` |
| GitHub EN | `OAUTH_GITHUB_EN_ENABLED` | `OAUTH_GITHUB_EN_CLIENT_ID` | `OAUTH_GITHUB_EN_CLIENT_SECRET` |
| GitHub RU | `OAUTH_GITHUB_RUS_ENABLED` | `OAUTH_GITHUB_RUS_CLIENT_ID` | `OAUTH_GITHUB_RUS_CLIENT_SECRET` |
| Facebook | `OAUTH_FACEBOOK_ENABLED` | `OAUTH_FACEBOOK_CLIENT_ID` | `OAUTH_FACEBOOK_CLIENT_SECRET` |
| LinkedIn | `OAUTH_LINKEDIN_ENABLED` | `OAUTH_LINKEDIN_CLIENT_ID` | `OAUTH_LINKEDIN_CLIENT_SECRET` |

Пример для локального `.env.local`:

```dotenv
OAUTH_GOOGLE_ENABLED=1
OAUTH_GOOGLE_ID=YOUR_GOOGLE_CLIENT_ID
OAUTH_GOOGLE_SECRET=YOUR_GOOGLE_CLIENT_SECRET
```

Не добавляйте реальные учётные данные в отслеживаемые файлы, документацию или журналы. Если переменная уже передана PHP-контейнеру как настоящая переменная окружения, `.env.local` её не переопределит; подробнее о приоритетах — в [руководстве по конфигурации](configuration.md).

Выключатель является серверной границей: значение `0` не просто скрывает кнопку, а закрывает начальный маршрут и маршрут возврата. Включённый провайдер без Client ID или Client secret отвечает контролируемой ошибкой сервера, не раскрывающей секрет. Не следует включать провайдера до заполнения обоих значений.

## Обычный вход и регистрация

Обычный сценарий начинается гостем с начального маршрута провайдера и возвращается на маршрут callback. Приложение применяет следующие правила:

### Уже связанный внешний ID

Если внешний ID найден в соответствующем уникальном поле, выполняется вход в ту же локальную учётную запись. Email от провайдера не заменяет локальный email, и успешный вход сам по себе не изменяет профиль или OAuth-связь. Удалённый локальный пользователь не допускается к входу.

### Неизвестный внешний ID и существующий локальный email

Вход отклоняется нейтрально. Приложение не привязывает провайдера по совпадению email, не создаёт пользователя, не меняет существующую запись и не отправляет регистрационное событие или письмо. Привязка возможна только отдельным сценарием из аутентифицированного личного кабинета.

### Неизвестный внешний ID и новый email

Создаётся новый локальный пользователь со следующими свойствами:

- email и внешний ID берутся из проверенного ответа провайдера;
- `isVerified=false`;
- локальный пароль генерируется из криптографически случайного значения и сохраняется только как хеш;
- пользователь сохраняется до формирования письма подтверждения;
- запускается стандартный сценарий подтверждения email;
- после успешной OAuth-аутентификации пользователь входит в приложение.

Транспорт почты по умолчанию — `null://null`, а ошибки транспорта при OAuth-регистрации нейтрализуются. Поэтому наличие сценария подтверждения не означает гарантированную внешнюю доставку письма без отдельно настроенного `MAILER_DSN`.

### Провайдер не вернул email

Если внешний ID ещё не связан, а email отсутствует или пуст, вход нейтрально отклоняется и пользователь не создаётся. Ошибки обмена токена или получения профиля также не должны раскрывать детали внешнего запроса пользователю.

## Явная привязка

Привязку начинает аутентифицированный локальный пользователь из личного кабинета.

1. `GET` открывает страницу подтверждения без изменения данных и без создания намерения.
2. `POST` требует корректный текущий пароль и CSRF-токен.
3. После проверки приложение выполняет OAuth-перенаправление и сохраняет одноразовое намерение в текущей сессии.
4. Обработчик callback сверяет пользователя, провайдера, state и срок жизни намерения.
5. Внешний ID записывается только если он ещё не принадлежит другому пользователю.

Намерение привязано к точному ID локального пользователя и точному провайдеру. В нём хранится SHA-256-хеш OAuth state, а не исходный state; срок жизни — 600 секунд. Попытка чтения намерения одновременно удаляет его из сессии, поэтому неверный callback тоже потребляет намерение, а повтор успешного callback отклоняется.

Привязка не заменяет локальный email данными провайдера. Конфликт занятого внешнего ID обрабатывается одинаково до проверки и на уровне уникального ограничения базы, без переноса идентичности между пользователями.

## Защищённая отвязка

Отвязка также доступна только аутентифицированному пользователю:

1. `GET` показывает форму подтверждения и не меняет внешний ID;
2. `POST` требует текущий пароль и CSRF-токен;
3. сервер сопоставляет значение `provider` с конкретным полем User;
4. обнуляется только выбранная связь, после чего изменения сохраняются.

Имя поля не принимается от клиента. Неизвестный провайдер или отсутствующая связь дают `404`. Если провайдер был выключен после создания связи, пользователь всё равно может безопасно его отвязать: выключатель блокирует новые OAuth-сценарии, но не оставляет старую связь без способа удаления.

## Маршруты

Все OAuth-маршруты находятся под префиксом `/{_locale}`, где текущие локали — `ru` и `en`.

| Провайдер | Начало | Callback |
| --- | --- | --- |
| Google | `/{_locale}/connect/google` | `/{_locale}/connect/google/check` |
| Yandex | `/{_locale}/connect/yandex` | `/{_locale}/connect/yandex/check` |
| VKontakte | `/{_locale}/connect/vkontakte` | `/{_locale}/connect/vkontakte/check` |
| GitHub EN | `/{_locale}/connect/github-en` | `/{_locale}/connect/github-en/check` |
| GitHub RU | `/{_locale}/connect/github-ru` | `/{_locale}/connect/github-ru/check` |
| Facebook | `/{_locale}/connect/facebook` | `/{_locale}/connect/facebook/check` |
| LinkedIn | `/{_locale}/connect/linkedin` | `/{_locale}/connect/linkedin/check` |

Начальный маршрут и callback используются браузерным GET-сценарием, однако текущая YAML-конфигурация не задаёт для них явного ограничения `methods` на уровне маршрутизатора. Это не следует документировать как гарантию маршрутизатора.

Явные операции личного кабинета имеют точные маршруты и методы:

| Операция | Маршрут | Методы |
| --- | --- | --- |
| Привязка | `/{_locale}/profile/oauth/{provider}/link` | `GET`, `POST` |
| Отвязка | `/{_locale}/profile/oauth/{provider}/unlink` | `GET`, `POST` |

Для `{provider}` используются значения `google`, `yandex`, `vkontakte`, `github_en`, `github_rus`, `facebook` и `linkedin`. Redirect URI в кабинете конкретного провайдера должен соответствовать его callback-маршруту и реальному базовому адресу среды.

## Граница владения идентичностью

Поля `google_id`, `yandex_id`, `vkontakte_id`, `github_id`, `facebook_id` и `linkedin_id` имеют уникальные ограничения Doctrine и базы данных. Это последняя защита от одновременной привязки одного внешнего аккаунта к двум локальным пользователям, включая состояние гонки.

Документация описывает контракт текущего кода и тестов, но не утверждает, что реальный сценарий каждого внешнего провайдера повторно проверялся при каждом изменении документации.
